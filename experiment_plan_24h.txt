24-HOUR EXPERIMENT: CAN MODELS ENGINEER THEIR OWN PREDICTABLE MISTAKES?
Draft, 15 November 2026. No API experiments have been run.

RECOMMENDATION

Build one mechanically checked puzzle experiment, using three models as both
authors and solvers. Start with small Sokoban boards. Test whether an author
can predict and induce one specific wrong first push in its own fresh solver
better than peer authors can. Then test whether a diagnostic warning helps.

Keep the claim conditional on the exact model, prompt, tools, and budget.
Generation being easier than solving, ordinary adversarial puzzle generation,
and benchmark renewal are already established. This study must establish
model-specific predictive value to carry an epistemics claim.

The proposed title is a question. Do not commit to "models foresee mistakes
but cannot avoid them" before collecting evidence. Target innovation 5 through
the finding and causal analysis; execution and clarity depend on what is
actually completed, not the ambition of this plan.

Confirmed constraints: 1-2 implementers and sponsor credits only. Use local
CPU and the Adaption access described in env_description.txt. External API
spending, paid cloud compute and credit top-ups are outside this plan.

1. EXACT EXPERIMENT

Fix a roster A, B, C. Each model receives the same game rules, solver prompt,
tool contract, resource limits, and factual descriptions/IDs of all three
models. Author A is genuinely model A; do not simulate identities by roleplay.

For every author, randomly assign generation slots to four objectives:
  - Target A's specific first-push mistake.
  - Target B's specific first-push mistake.
  - Target C's specific first-push mistake.
  - Produce a generically difficult trap for this pool of solvers.

Every author produces 24 slots per objective: 3 x 4 x 24 = 288 slots.
Each slot permits an initial proposal and at most one validity-only repair.
Accept the first valid, nonduplicate proposal. Preserve rejected attempts and
failed slots. Authors never see solver outcomes for their proposed puzzles.

Each proposal contains:
  - A 7x7 Sokoban board with 2-3 boxes and equally many goals.
  - One legal initial box push predicted to be attractive to the target.
  - A complete winning sequence, to establish that a solution exists.
  - For each solver: P(predicted first push) and P(full solution).
  - A short explanation and a mechanism-level diagnostic warning.

The evaluator independently confirms that the declared first push makes the
puzzle unsolvable. The predicted event is therefore exact and observable.
There can be many correct solutions; accept all of them.

Every accepted puzzle is attempted by every solver twice in fresh contexts.
Add 32 procedurally generated puzzles meeting the same mechanical filters.
At full validity this gives (288 + 32) x 3 x 2 = 1,920 main solver episodes.
Repeated samples estimate stochastic behavior; the independent evidence is
primarily the number of distinct puzzles, not the number of API requests.

2. GAME AND SOLVER HARNESS

Use a tiny custom Sokoban implementation, not a commercial game integration.
Supply both the board and structured coordinates. Use macro-push actions:
push a particular box in a direction, with ordinary walking to the box handled
by the engine. This removes irrelevant walking and coordinate-parsing errors.

All solvers receive the same interface:
  - Legal current pushes.
  - Up to two simulate_plan calls, each replaying at most 40 pushes on a copy.
  - A final submitted plan of at most 40 pushes.

Simulations report the resulting board, completion, and illegal actions. They
do not reveal deadlock labels, a reference solution, or optimal distances.
Only the final submitted plan counts as committed behavior. Exploring a bad
move during simulation is legitimate investigation, not a scored mistake.

Primary bounds: at most three model requests, 180 seconds per episode, and a
4,000-token generated-output planning envelope, including reasoning where the
provider accounts for it. Reserve around 10,000 input tokens per episode.
Enforce provider-native output limits and reconcile actual usage; the input
number is a planning estimate. Record native effort/sampling settings, context
and usage. Equal nominal tokens do not establish equal compute across models.

The primary harness has no arbitrary Python execution. Report that plainly.
Include a conventional planner as a baseline so failure cannot be presented
as evidence that the puzzle is computationally intractable. An unrestricted
code-agent study is a later experiment, not a hidden change of this protocol.

Keep author explanations, forecasts, witnesses, IDs, target assignments,
oracle statistics, and warnings out of normal solver inputs. Never tell a
solver to make the predicted mistake. Disable cross-episode memory and model
routing. Do not use persistent inference stacks with unknown instructions.

3. DATASET AND MECHANICAL VALIDATION

No purchased or training dataset is needed. Build a procedural development
bank and the new authored evaluation set. Avoid famous published levels.

Before any model experiment, build:
  - A direct grid replay checker.
  - An independently implemented push-space breadth-first oracle.
  - Procedural valid-level generation and symmetry canonicalization.

For each proposal check:
  - Board syntax, boundary walls, one player, box/goal counts and nonterminal
    start; all coordinates/actions in range.
  - The author's witness wins in both independent implementations.
  - A winning plan exists; provisionally require 6-30 optimal pushes.
  - The declared initial push is legal and its successor has no solution.
  - No duplicate under rotations, reflections, box permutations and equivalent
    player positions in the same reachable region.

Search cap: 100,000 states / 5 seconds per oracle query initially. If a search
hits a cap, label UNKNOWN. A timeout is never proof of unsolvability. Exclude
unresolved puzzles from valid-puzzle behavior scores while retaining the slot
and reason in the dataset. Pilot can change bounds before the protocol freeze.

File layout to implement:
  src/game.py             direct transitions and plan replay
  src/oracle.py           independent reachability and optimal-push search
  src/generate.py         procedural bank and author generation/repair
  src/providers.py        provider adapters, usage, retries and fixed IDs
  src/runner.py           resumable randomized episode jobs
  src/metrics.py          event scoring and locked analyses
  tests/                 deterministic fixtures and cross-checks
  data/pilot/            development only
  data/main/             frozen accepted/rejected proposals and manifests
  runs/                  raw API responses, tool traces, costs, run records
  results/               tables, figures and illustrative replays

Use atomic JSON files per job/request and JSONL for export. Save prompt hashes,
code revision, model IDs/response metadata, sampling settings, all attempts,
timestamps, costs, action traces and validity certificates. Solver-facing data
is generated by a strict allowlist, not by deleting a few metadata fields.

4. CORE ANALYSIS

Let delta(a,t) be the average, over author a's slots targeting t, of:
  validity x [trap frequency of t - mean trap frequency of the other solvers].

Primary statistic:
  D = mean delta(a,a) - mean delta(a,t) for a != t.

This asks whether self-targeting has an advantage over equally budgeted peer
authors targeting the same models. A puzzle that defeats everyone contributes
little target-specific advantage. Invalid slots contribute zero generation
credit, preventing selective removal of failed construction attempts.

Also report D conditional on valid puzzles, validity yield per condition,
targeted-versus-generic differences, full solve rates, and Brier scores for
precommitted forecasts. Use per-solver base-rate forecasts estimated from the
disjoint pilot as a simple calibration baseline. A positive generation effect
without predictive value should not be sold as demonstrated self-knowledge.

Use a two-sided 95% stratified cluster bootstrap over generation slots within
author/target cells (10,000 resamples); carry all repetitions/variants of a
puzzle together. Show each author's result separately. These three selected
models are not a random sample of all LLMs.

The sample is intended for large effects. A rough independent-Bernoulli
calculation with moderately correlated repeated runs puts detectable effects
around 20 percentage points, not a few points. Actual uncertainty depends on
puzzle heterogeneity; report intervals and do not present a weak null as proof
that self-knowledge is absent.

Distinguish: predicted bad push; another wrong push; illegal/invalid plan;
correct plan; model budget exhaustion; transport/API failure. A completed but
wrong model answer is never retried as an infrastructure error. Retry genuine
transport errors at most twice, logging each charge; never silently replace
a model. Report both unconditional completion and conditional behavior.
Unresolved service failures are missing observations, not zero-error results.
Report missingness by cell, use complete solver panels for the primary
estimate, and give worst-case bounds for missing observations. A terminal
status and separate error/success flags avoid overlapping error categories.

5. WARNING EXPERIMENT

Preselect ALL valid self-targeted main puzzles by assignment, before looking
at solver outcomes: up to 72 puzzles. Run only the corresponding target model,
twice under each additional arm:
  - Generic caution.
  - Author's diagnostic warning.
  - Independently written peer diagnostic warning.

Reuse the no-warning main runs as baseline. This adds at most 432 episodes.
The peer sees the same board, verified witness, bad-push specification and
solver contract; it sees no author forecast, author warning or solver results.
Assign peers in a balanced cycle. Do not label warning provenance to the actor.

Warnings are at most 40 words and discuss a mechanism. Exclude coordinates,
directions, solution prefixes and explicit bans on the predicted action.
Review them blind to outcomes; otherwise a gold-action hint could masquerade
as metacognitive improvement. Length-match generic cautions approximately.
Mark noncompliant warnings unavailable and report these counts; retain the
puzzle in the baseline and primary analyses. Never revise warnings using
observed solver outcomes.

Measure both specific-error reduction and full-solution improvement. Avoiding
the first bad push by refusing to act is not a repair. Apply Holm correction
to the three warning-versus-baseline comparisons. Include all preselected
puzzles, not only those where the no-warning solver happened to fail.

If warnings help, that is evidence of usable diagnostic information. If they
do not, inspect interval width and prompt quality before claiming a gap
between knowledge and control. Warning text can also prime a mistake.

7. TESTS AND PILOT GATES

Engine tests: wins, illegal moves, corners, wall locks, multi-box interference,
and puzzles with more than one winning route. Check box conservation and fixed
walls. Compare both implementations on exhaustively enumerable tiny boards;
replay oracle solutions independently. Symmetry must preserve reachability
and optimal push count and transform the predicted bad action correctly.

Pipeline tests: mock provider responses, interrupted-job resume, duplicate
responses, malformed JSON, missing usage, rate limits, deterministic grading,
and a leakage test confirming private author/oracle fields never enter actor
inputs. Verify all scored episodes are either recorded once or explicitly
marked unfinished/failed.

Pilot: 24 authored slots (two per cell), no reuse in the main experiment.
Gate at hour 6 on:
  - Zero unresolved checker disagreements.
  - Around 70% or better author validity after the fixed repair budget.
  - Nontrivial first-push and solve behavior: avoid near-zero or near-total
    failure across every model. Adjust difficulty once using pilot only.
  - Measured throughput and cost fit the remaining window with reserve.

Do not require a significant self-targeting effect in the pilot. It is too
small for that. Freeze the code revision, prompts, roster, effort, sizes,
manifests, outcomes and analysis before generating the main dataset.
If feasibility fails, reduce scope or report the limitation; do not relabel a
generic generation-versus-solving result as the planned epistemic discovery.

For two implementers, one owns engine/validation/data and one owns API runner,
analysis/report; both independently inspect checker behavior and sample traces.
For one implementer, drop optional audits before cutting core controls or the
last six hours. This plan does not spawn or assume autonomous sub-agents.

If projected throughput is insufficient, select the predeclared reduced plan
BEFORE main generation: 12 slots per cell instead of 24, with wider intervals.
Do not choose sample size based on emerging effect sizes. Add unique puzzles
before increasing repetitions beyond two when time is available.

9. DELIVERABLE AND JUDGING STRATEGY

Deliver a reproducible dataset with witnesses, forecasts, exact error labels,
rejected attempts, prompts, costs and traces; a checker; and one clear finding.
Three figures are enough: author-target specificity matrix, forecast versus
observed error, and randomized warning effects on errors/full success.

Use the official <=8-page report template, a 150-250-word abstract, and the
required Limitations and Dual-Use / Ethical Considerations appendix. State
that puzzle findings do not establish consciousness or general introspection,
and that targeted-error generation can be used to manipulate as well as audit
systems. No private/personal dataset is needed.

equivalent to 16 November 2026, 11:59 UTC. A 24-hour run from the current early
15 November UTC planning time fits within it; use a six-hour analysis buffer.
